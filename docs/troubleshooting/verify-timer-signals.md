# Verify timer and daemon signals (verified / FAILED / drift)

## Symptom

The 15-minute verify timer or your workload's daemon unit reports
something unexpected in the journal — and you need to know which
lines are healthy.

## The services and their signals

| Unit | Runs as | Purpose | Log |
|---|---|---|---|
| `egresslock-verify@<account>.timer` | (timer) | 15-min drift signal, `Persistent=true` | `journalctl -t systemd` / `list-timers` |
| `egresslock-verify@<account>.service` | the account | `egresslock-verify`: profiles with a running anchor (`verify --ensured`) | `sudo journalctl -u egresslock-verify@ACCOUNT.service` |
| your workload's daemon unit (e.g. a runner service) | the account | `egresslock-start`: `ensure` (fail closed) then exec | `sudo journalctl -u DAEMON.service` |

Signal semantics (learned the hard way — check for these):

- Healthy: `profile '<name>' verified (ensured)` lines, exit 0.
- `warning: the account lock could not record who holds it (<lockf>): the lock is held for this run; a later "another egresslock command is running" message may show "holder: unknown" or a stale record` / **rc unchanged**: the account home was full when verify wrote its holder record; the lock is still held and verify continues. Free space on the account home; see [disk-full](disk-full.md).
- `verify: unfinished revocation for profile '<p>' — ...` / exit 1:
  a `disallow <p> <host:port> --direct` was interrupted after the conf
  rule was removed and the ruleset swapped but before its connections
  were proven ended; the durable record is
  `<confdir>/<p>.revoke-pending`. The flow may still be up until the
  heal: run `egresslock ensure PROFILE` as the account — it ends the
  recorded connections and clears the record. `verify` and the timer
  never repair; the `--ensured` sweep adds `verify: profile '<p>'
  FAILED revocation verification` and continues the other profiles. A
  corrupt or unreadable record fails the same named way (fail closed).
- `verify: ... FAILED` / exit 1: policy drift or a half-dead profile
  (e.g. gateway container down). Heal with `ensure <profile>` **as the
  account**; verify never auto-fixes. The kit's `egresslock-setup
  doctor` reports the same exit-1 instance with its last and next run,
  a `systemctl start` re-run command (its output goes to the service
  journal — the `sudo journalctl -u` line in the table above is where
  the details are), and, when the run itself passed an explicit
  `--profile`, the scoped repair `sudo -iu ACCOUNT -- egresslock ensure
  PROFILE`.
- `verify: policy chain p_PROFILE does not match the expected ruleset
  (the live chain is not what this engine would install now — often
  after an upgrade or a conf change) — run as <account>: egresslock
  ensure <profile>` / exit 1: the primary drift line — the profile's live
  nftables policy differs from what this engine would install.
  Heal with `ensure <profile>` **as the account**.
- `verify: shared v6-deny chain missing or does not match the expected
  policy (the live chain is not what this engine would install now —
  often after an upgrade) — run as <account>: egresslock ensure
  <profile>` / exit 1: the shared IPv6-deny chain is missing or stale. Same
  remedy: `ensure <profile>` **as the account**.
- `verify: anchor <name> not running` / exit 1: the profile's anchor
  container is gone (killed, removed, or lost at a reboot).
  `podman ps -a` shows it; heal with `ensure <profile>` **as the
  account** (or `egresslock-start`, which ensures then execs).
- A failed verify **timer** (rather than the service) means the timer
  could not start and the verify service never ran: its journal, not
  the service log, is the evidence. Doctor checks the timer's armed
  state first and names it: a disabled timer is reported as disarmed
  (with the re-arm command), masked/static/not-found states get their
  own fix, and an enabled-but-failed timer prints `reset-failed` +
  `restart` plus the timer journal. A stale failure stays visible until
  it is cleared — `enable --now` does not clear it.
- `verify: gateway container '<name>' not exec-able (...)` / exit 1:
  the gateway was stopped or mid-restart when verify inspected it —
  commonly a concurrent `disallow` or a fallback restart (a concurrent
  `ensure`/`allow` reloads in place and never stops the container; a
  bootstrap or first apply and `--replace-gateway` restart too).
  Not a config fault. Re-run after the concurrent command finishes —
  or `egresslock ensure PROFILE` **as the account** if the gateway
  stayed down. Only `verify: gateway squid config invalid: ...` means
  Squid itself rejected the deployed config.
- `verify: the deployed gateway configuration has no live configuration
  check (it was generated by an older egresslock)` / exit 1: this
  profile's gateway config predates the live-config probe. One-time
  after an upgrade: run `egresslock ensure PROFILE` **as the
  account**; verify never repairs or reloads.
- `verify: the deployed gateway allowlist file '<name>' no longer
  matches the checksum in its name (...)` / `verify: the deployed
  gateway configuration does not match the token embedded in it (it was
  edited after generation)` / exit 1: the deployed files changed after
  generation (an in-place edit or corruption), not workload drift.
  Re-ensure to regenerate; do not edit `/etc/squid/egresslock/*` by
  hand. An unreadable group or deployed config names that instead.
- `verify: the running gateway did not return the live configuration
  check redirect (...)` / exit 1: the single loopback request did not
  get a 302 with the exact `Location`. The running Squid may still be
  serving an earlier configuration or be mid-reload — commonly a
  concurrent `ensure`/`allow`. Re-run after the concurrent command
  finishes; if it persists, `egresslock ensure PROFILE` **as the
  account**.
- `verify: the running gateway is serving a different configuration
  than the deployed <cfgdir>/squid.conf (...)` / exit 1: the deployed
  config is not what the running Squid loaded (for example a
  post-publish interruption). Re-ensure; verify only observes and never
  reloads.
- `status=203/EXEC` (systemd start failure, no verify output at all):
  the unit file itself is broken — e.g. a stale template left in
  `/etc/systemd/system` shadowing the package's unit after a
  prefix→deb switch. Run `sudo egresslock-setup doctor`: it names
  the shadowing file (or missing ExecStart target) and the exact fix.
  When that verify-unit row already explains the failed instance,
  doctor reports the instance as a note instead of a second problem
  (no repeated target/reinstall text); a 203/EXEC it cannot explain
  keeps the service journal as the lead evidence.
  If the shadow is the postinst co-install refusal (the `.deb` install
  FAILED because a prefix kit was still installed): remove the prefix
  kit with `uninstall-kit.sh`, then finish the install with
  `sudo dpkg -i DEB` or `sudo apt-get install -f` — **not**
  `apt-get install --reinstall egresslock`, which cannot resolve the
  half-installed (`iF`) state ("No file name for egresslock").
- `drift: host <name> resolved to <new> but the policy pins <old>`:
  the host's address set changed at `ensure` time (a member address
  appeared or disappeared — a resolver reorder of the same addresses
  is not a change; multi-address values render comma-joined); policy
  is unchanged; `ensure` heals on the next run. The pinned set is
  capped at the first 16 sorted distinct addresses (`DNS_SET_MAX`); a
  larger answer truncates with a named `note:`.
- `verify: cannot write the temporary expected-ruleset file in /tmp; the policy could not be checked (exit 1)` / **exit 1**:
  `/tmp` is full or otherwise unwritable, so verify could not build
  its expected ruleset. The policy was **not checked** — this is not
  drift, and no `policy chain … does not match` line follows. Free
  `/tmp` space and re-run verify; do not re-ensure for this line alone.
  See [disk-full](disk-full.md).
- `verify: unexpected chain '<name>' in the egresslock firewall table (no profile config in <confdir> defines it)` / **exit 1**:
  the account's `inet egresslock` table holds a chain no profile
  config defines — commonly a `p_<name>` chain left behind by an
  older engine's `teardown` or by a teardown that could not remove
  it (current `teardown` removes the profile's chain itself), or a
  chain someone added by hand. Verify is read-only (the 15-minute
  timer stays red). **`ensure` of any remaining profile removes it**:
  it prints `ensure: removed unexpected chain '<name>'` and then
  proves the table is clean. You can also remove it by hand (flush
  first — a rule-bearing chain cannot be deleted):
  `podman unshare --rootless-netns nft flush chain inet egresslock 'NAME'`,
  then `podman unshare --rootless-netns nft delete chain inet egresslock 'NAME'`.
  The Delete-a-profile step in the
  [policy reference](../reference/policy-reference.md) carries the
  same cleanup.
- `verify: cannot read the egresslock firewall table; the policy could not be checked (exit 1)` / **exit 1**:
  the chain checks passed, but verify could not read the table to look
  for chains no profile config defines. **No drift result was
  determined** — this is not an `unexpected chain` line and no
  `policy chain … does not match` line follows. Re-run verify; if it
  repeats, check podman/pasta health and the
  [netns inspection](netns-inspection.md) page. Do not re-ensure for
  this line alone.
- A name that serves **one address per query from a rotating pool**
  (e.g. `github.com` over SSH) is the exception: each `ensure` pins
  only the one answer it saw, so a later cycle that resolves another
  member warns again, and re-`ensure` only swaps which member is
  pinned. Replace the name with one IPv4-literal
  `allow-host` line per member (literals never resolve, so they never
  drift), or tunnel the connection through the gateway by name — see
  [Rotating names](../reference/rotating-names.md).
- `verify: network exists but policy does not — run as <account>:
  egresslock ensure <profile>` / exit 1: the post-reboot stale
  window — the profile's podman network object survived the reboot (on
  disk) but the netns policy is gone (volatile). Heal with `ensure
  <profile>` **as the account**; the timer never re-ensures. This is
  the default sweep-mode timer's post-reboot drift signal.
- SILENT exit 0 from `--ensured` means "no profile with a running
  anchor **and** no stale leftovers" — if you expected anchors, that
  itself is the signal (e.g. wrong XDG_RUNTIME_DIR context; the kit
  entry scripts resolve it from the uid, so check how the unit was
  invoked). A post-reboot stale profile is **not** silent: it fails
  named with the line above. A stopped anchor whose chain is still
  installed is silent too — silence does not mean nothing is ensured
  (see [after-a-reboot](after-a-reboot.md)).
- `egresslock denied PROFILE` lists hosts the gateway blocked
  (de-duplicated) — feed candidates to `allow <profile> <host:port>`
  (see [gateway-logs](gateway-logs.md)).

## Quick status, as the account

- `podman images` shows the gateway image.
- `podman ps -a` shows the anchor/gateway containers.
- `systemctl status egresslock-verify@ACCOUNT.service` (system
  scope, NOT `--user`) shows the last verify run.
